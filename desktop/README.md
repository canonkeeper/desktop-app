# Оболочка настольного приложения CanonKeeper

Оболочка на Tauri 2: запускает бэкенд (`backend/cmd/desktop`) рядом с собой, открывает окно на его адресе
`http://127.0.0.1:P/`, говорит понятными словами, если бэкенд не стартовал, и собирается в установщики Windows (NSIS
для текущего пользователя) и Linux (`.deb`, `.rpm`, AppImage). Бизнес-логики в ней нет.

- `src-tauri/` — крейт окна; `src-tauri/crates/core/` — всё, что можно проверить без окна: канал управления, пути,
  слова при сбоях, куда окну можно ходить, надзор за бэкендом.
- `app/` — страница, которую оболочка несёт с собой: «CanonKeeper запускается…» и окно ошибки.
- `release.json` — что приходит извне с закреплённым sha256: пакет Codex (версии `backend/go.mod`), исходники
  PostgreSQL (`postgres/` собирает из них набор PostgreSQL) и файлы, которые бандлер Tauri берёт в установщик.
- `release-notes.txt` — текст выпуска версии, которая выходит следующей: простой текст до 8 КиБ.
- `ci/desktop-build.yml` и `ci/forbidden.yml` — workflow публичного репозитория: сборка установщиков, дымовые прогоны,
  выпуск и проверка запрещённого содержимого. Выгрузка кладёт их в его `.github/workflows/`; своих workflow у
  публичного репозитория нет. Рядом — их сценарии: `ci/smoke.mjs`, `ci/smoke-update.mjs`, `ci/bundler-tools.mjs`,
  `ci/release-body.mjs`, `ci/pkexec.sh`.

## Что нужно для сборки на Linux (Ubuntu 24.04)

- Rust 1.96, Node.js версии `.node-version`, Go версии `backend/go.mod`, `gh` (скачать пакет Codex).
- Пакеты системы:
  `sudo apt install build-essential file libwebkit2gtk-4.1-dev librsvg2-dev patchelf rpm`.
- Для набора PostgreSQL: `sudo apt install bison flex python3-pip` и `pip install meson ninja`.
- Tauri CLI 2.12.4: `npm ci --prefix desktop` (из `desktop/package-lock.json`).

## Как собрать и запустить

1. Ядро оболочки — на любой машине, без системных библиотек окна:
   `cd desktop/src-tauri && cargo test -p canonkeeper-desktop-core`.
   Сборка под Windows — перед выгрузкой, на машине разработки: `npm run check:desktop:windows` (`cargo clippy -D
   warnings` под `x86_64-pc-windows-msvc` для обоих крейтов со всеми целями, как выпуск и как дымовая сборка). Ничего не
   линкуется: вне Windows архиватор и компилятор ресурсов Windows, которых просят сценарии сборки `ring` и `tauri-build`,
   заменены заглушкой, C-код `ring` идёт компилятором C системы. Без цели (`rustup target add x86_64-pc-windows-msvc`)
   проверка говорит, что пропущена, и кончается успехом. Линковку, установщик и тесты под Windows проверяет только CI.
2. Набор PostgreSQL из закреплённых исходников:
   `python3 -I desktop/postgres/build.py /tmp/pg-work /tmp/pg-out && tar -cf /tmp/pg-set.tar -C /tmp/pg-out .`
3. Пакет Codex — тег и имя из `desktop/release.json`, например:
   `gh release download rust-v0.165.4 -R Dirard/codex -p codex-package-x86_64-unknown-linux-gnu.tar.gz -D /tmp/codex`.
4. Набор: `node scripts/desktop-app.mjs --target x86_64-unknown-linux-gnu --postgres /tmp/pg-set.tar --codex
   /tmp/codex/codex-package-x86_64-unknown-linux-gnu.tar.gz`. Сценарий сверяет sha256 с `release.json` (несовпадение —
   отказ), собирает бэкенд с вебом и раскладывает всё в `desktop/bundle`. Сам он ничего не скачивает.
5. Установщики: `cd desktop && npx tauri build --config src-tauri/tauri.bundle.json --bundles deb,rpm`; AppImage —
   `--bundles appimage`. Готовое — в `desktop/src-tauri/target/release/bundle/`.
6. Запуск: `sudo apt install ./desktop/src-tauri/target/release/bundle/deb/*.deb`, затем `canonkeeper`. Данные — в
   `~/.local/share/canonkeeper` (на Windows — `%LOCALAPPDATA%\ru.canonkeeper.desktop\data`, отдельно от программы),
   журнал оболочки — `logs/shell-<дата>.log` там же: в нём только события, без адресов, кодов и текстов. Файлы, которые
   сохраняет приложение («Скачать книгу…», файл главы), ложатся в папку загрузок системы под свободным именем; на Linux
   без папки загрузок — в домашнюю папку.

## Что удаляет «Стереть все данные»

«Настройки → Данные → Стереть все данные…» и слово «стереть» (`specs/2026-11-13-desk-erase.md`): бэкенд передаёт просьбу
оболочке по каналу управления, оболочка ставит отметку, останавливает бэкенд, закрывает окно и удаляет:

- каталог данных целиком — базу, `settings.json`, `secrets.json`, дома Codex, журналы, копии перед обновлением и папки
  «до возврата» `before-restore-*` (`%LOCALAPPDATA%\ru.canonkeeper.desktop\data`; `$XDG_DATA_HOME/canonkeeper`, иначе
  `~/.local/share/canonkeeper`); PostgreSQL приложения, если он ещё работает в каталоге данных (бэкенд был остановлен
  принудительно), сначала останавливается программой набора;
- данные окна — `localStorage`, cookie и кэш веб-движка — и кэш приложения: на Windows весь
  `%LOCALAPPDATA%\ru.canonkeeper.desktop`, на Linux `$XDG_DATA_HOME/ru.canonkeeper.desktop` и
  `$XDG_CACHE_HOME/ru.canonkeeper.desktop` (иначе `~/.local/share/…` и `~/.cache/…`);
- записи службы `CanonKeeper` в хранилище ключей системы (Credential Manager, Secret Service).

Остаются установленная программа, файлы, которые автор сохранил сам (книги, главы, файлы саги), и папки Obsidian;
по ссылкам из каталогов приложения удаление не ходит. Удаляется только каталог, чьё собственное имя — имя приложения
(`canonkeeper` и `ru.canonkeeper.desktop` на Linux, `ru.canonkeeper.desktop` и его `data` на Windows), не дом и не выше
него, без `..` в пути; если сам каталог приложения автор перенёс и оставил на его месте ссылку, а она ведёт в каталог с
тем же именем, удаляется и он. Отметка — `ru.canonkeeper.desktop.erasing` рядом с каталогом идентификатора; если файл был
занят другой программой или хранилище ключей не удалило запись, следующий запуск заканчивает удаление до бэкенда и окна,
а не сумев — говорит, какая папка занята или что ключ остался, и бэкенд на недостёртых данных не запускает. Если
отметку нельзя поставить (нет записи на диск, место с `..`) или в каталоге данных лежит чужое и нет ничего от
приложения (базы, `settings.json`, `secrets.json`, журнала оболочки), стирание не начинается: окно говорит «Стирание не
началось» и где лежат книги.

## Новая версия и возврат данных из копии

`specs/2026-11-13-desk-upgrade.md`. Оболочка и бэкенд — одна версия: бэкенд другой версии (установка оборвалась
посередине) не трогает данные и окно запуска просит поставить ту же версию ещё раз. Первая программа новой версии на
данных прежней делает копию `backups/pre-<последняя миграция>-<время UTC>/` (база `db.dump`, дома Codex, версия
программы, главная версия PostgreSQL) и применяет миграции; Job, брошенные прежней программой, ей не мешают — их доводят
воркеры новой. Пока идут копия и миграции, окно запуска говорит, что идёт. Версия, открывавшая данные, лежит в
`settings.json` (`version`).

Прежняя версия на данных новой не стартует: окно запуска называет версию, открывавшую данные, и, если есть копия, чью
схему и PostgreSQL прежняя версия знает, предлагает «Вернуть данные из копии…». Возврат восстанавливает базу и дома
Codex из копии рядом с данными (`pg.restoring`, `codex/*.restoring`) и только после удачного восстановления переносит
нынешние данные в папку «до возврата» `<каталог данных>/before-restore-<время UTC>/` (`pg`, `codex/home`,
`codex/sqlite`), а восстановленные ставит на их место. Отметка `restoring` в каталоге данных стоит, пока возврат идёт:
любой следующий запуск, найдя её, сначала возвращает всё на место. Файлы саги (`files/`: обложки, картинки) возврат не
трогает. Копия остаётся в `backups/`.

Папки «до возврата» приложение не удаляет никогда; каждый возврат оставляет свою. Чтобы вернуться к данным из такой
папки (например, после установки новой версии снова):

1. Закройте CanonKeeper.
2. В каталоге данных переименуйте нынешние `pg`, `codex/home` и `codex/sqlite` (например, добавьте `.old`) — или
   перенесите их в другую папку.
3. Перенесите `pg`, `codex/home` и `codex/sqlite` из папки `before-restore-…` на их места в каталоге данных.
4. Запустите версию CanonKeeper, которая эти данные открывала (или новее): она откроет их как есть.

## Обновления приложения

`specs/2026-11-13-desk-updates.md`. Раз в сутки (первый раз — через полминуты после запуска), если автор оставил
ежедневную проверку включённой, оболочка спрашивает о новой версии по постоянному списку адресов: сайт
(`https://canonkeeper.ru/app/open/latest.json`), затем выпуски `canonkeeper/desktop-app` на GitHub. Запрос — только
`https`, только к хостам списка (`canonkeeper.ru`, `github.com`, `release-assets.githubusercontent.com`), без
сведений об авторе и компьютере. Сведения о версии (`latest.json`) принимаются, только если их подпись
(`latest.json.sig`) сделана основным или запасным ключом приложения; файл новой версии — только с подписью, которая
называет его версию. Ставит обновление автор кнопкой «Обновить и перезапустить»: файл скачивается и проверяется,
идущий ответ помощника доходит до конца, окно уходит на страницу запуска, бэкенд останавливается сам вместе с
PostgreSQL и Codex, и только тогда идёт установка (Windows — установщик NSIS с окном хода; Linux — AppImage заменяется,
пакет `.deb`/`.rpm` ставит `pkexec` через `apt-get install` или `dnf install`, пароль спрашивает только система). Любой
отказ до перемены программы возвращает рабочее окно на тех же данных. Сборка из исходников и AppImage, распакованный
из файла, обновляются вручную.

## Вернуться на прежнюю версию

Данные новой версии прежняя версия не откроет: окно запуска скажет, какая версия их открывала, и, если есть копия
перед обновлением, предложит «Вернуть данные из копии…». Сама прежняя версия ставится поверх новой так:

- **Windows.** Запустите установщик прежней версии (`CanonKeeper_<версия>_x64-setup.exe`). Он предложит удалить
  установленную версию перед установкой — согласитесь и **не** отмечайте «Удалить данные приложения»: тогда книги и
  настройки останутся.
- **Ubuntu, Debian (`.deb`).** `sudo apt install --allow-downgrades ./CanonKeeper_<версия>_amd64.deb`
- **Fedora, openSUSE (`.rpm`).** `sudo dnf downgrade ./CanonKeeper-<версия>-1.x86_64.rpm` (openSUSE —
  `sudo zypper install --oldpackage ./CanonKeeper-<версия>-1.x86_64.rpm`)
- **AppImage.** Скачайте файл прежней версии (`CanonKeeper_<версия>_amd64.AppImage`), сделайте его исполняемым
  (`chmod +x`) и запускайте его вместо нынешнего.

Файлы каждой версии — на странице её выпуска: `https://github.com/canonkeeper/desktop-app/releases/tag/v<версия>`.

## Выпуск

Выпуск — метка `vX.Y.Z` на `main` публичного репозитория; `X.Y.Z` — версия `src-tauri/Cargo.toml`, текст выпуска —
`release-notes.txt` этой версии. Сценарий `ci/desktop-build.yml` на метке собирает установщики (без секретов, только
чтение), отдельным заданием без кэша собирает инструмент выпуска `canonkeeper-release` (`src-tauri/crates/core`), затем
задание подписи в окружении `release` сверяет инструмент по сумме и подписывает основным ключом: каждый установщик — с
версией в подписи, `latest.json` с файлом на каждый вид установки (`windows-x86_64-nsis`, `linux-x86_64-deb`,
`linux-x86_64-rpm`, `linux-x86_64-appimage`) и его подпись, `latest-site.json` с теми же файлами по их адресам на сайте и
его подпись, `SHA256SUMS` и его подпись. До черновика тот же инструмент проверяет выпуск тем же кодом, что приложение:
метка равна версии оболочки, `latest.json`, `latest-site.json` и каждой подписи; в обоих манифестах подпись каждого вида —
та же, что в `.sig` его файла, а в `latest-site.json` каждый файл ровно по адресу
`https://canonkeeper.ru/app/open/<версия>/<файл>`; каждая подпись проходит по основному ключу дерева метки (константа
`MAIN_KEY` ядра и `plugins.updater.pubkey` в `tauri.conf.json`), ключ разработки — отказ; на каждый вид ровно один файл;
программа каждого пакета несёт метку своего вида и не несёт метки дымовой сборки. Затем — свидетельство сборки GitHub
(attestation) и черновик выпуска со всеми файлами и разделом «Вернуться на прежнюю версию»; публикует его владелец.

Файлы выпуска — 14:

- установщики `CanonKeeper_<версия>_x64-setup.exe`, `CanonKeeper_<версия>_amd64.deb`, `CanonKeeper-<версия>-1.x86_64.rpm`,
  `CanonKeeper_<версия>_amd64.AppImage` и подпись каждого рядом с ним: `CanonKeeper_<версия>_x64-setup.exe.sig`,
  `CanonKeeper_<версия>_amd64.deb.sig`, `CanonKeeper-<версия>-1.x86_64.rpm.sig`, `CanonKeeper_<версия>_amd64.AppImage.sig`;
- `latest.json` и `latest.json.sig` — версия для приложения с файлами в выпуске на GitHub;
- `latest-site.json` и `latest-site.json.sig` — та же версия с теми же подписями, но с файлами на сайте
  (`https://canonkeeper.ru/app/open/<версия>/<файл>`). Сайт сам держит копию последнего опубликованного выпуска: скачивает
  его, проверяет подписи ключами приложения и только тогда отдаёт этот файл как `https://canonkeeper.ru/app/open/latest.json`,
  а установщики — по их адресам на сайте. Пока копии нет или она отстала от GitHub, сайт на этот адрес отвечает 404, и
  приложение узнаёт о версии и скачивает её с GitHub;
- `SHA256SUMS` и `SHA256SUMS.sig` — суммы всех файлов выпуска и их подпись.

Шаги владельца до первого выпуска:

1. Две пары ключей на своём компьютере инструментом выпуска `canonkeeper-release keygen` (в `src-tauri/`:
   `cargo run -p canonkeeper-desktop-core --bin canonkeeper-release -- keygen main.secret`, затем `… keygen
   spare.secret`). Каждая команда пишет закрытую половину в новый файл только для своего пользователя и печатает
   открытую.
2. Открытые половины — в приложение: основная — `MAIN_KEY` в `src-tauri/crates/core/src/update/policy.rs` и
   `plugins.updater.pubkey` в `src-tauri/tauri.conf.json`, запасная — `SPARE_KEY`. Пока в дереве стоят ключи
   разработки, закрытых половин которых нет нигде, выпуск по метке падает на проверке. Те же открытые половины тем же
   изменением получает и сайт: он проверяет ими копию выпуска, и выпуск сайта с новыми ключами идёт раньше метки
   приложения — иначе сайт не откроет новую версию.
3. Окружение `release` в настройках репозитория: обязательный проверяющий — владелец, «Deployment branches and tags» —
   только метки `v*`; секрет окружения `CANONKEEPER_UPDATE_KEY` — содержимое `main.secret`. Правило репозитория: метки
   `v*` создаёт только владелец.
4. Запасной закрытый ключ хранится у владельца вне GitHub. Им выпускается версия после потери или утечки основного: в
   ней запасной становится основным (`MAIN_KEY`, `pubkey`, секрет окружения), а запасным — новая пара; сайт получает их
   так же, как в шаге 2.

## Что проверяет CI

Задания `ubuntu-24.04` и `windows-2025`: формат и тесты ядра, clippy окна; набор PostgreSQL из исходников по sha256;
набор приложения по закреплённым sha256; файлы бандлера по суммам `release.json` до сборки и после неё; `tauri build`;
три программы каждого пакета — оболочка с меткой своего вида, бэкенд и мост, ни одна не из дымовой сборки (пакет
распакован целиком, `.rpm` — `bsdtar`; отказ называет пакет и программу); дымовой прогон установленного приложения — запуск, окно получило страницу
бэкенда после обмена кода, остановка без оставшихся процессов бэкенда, PostgreSQL и Codex; на Windows — что удаление
без флажка «Удалить данные приложения» оставляет данные. Дымовой прогон обновления (`ci/smoke-update.mjs`, своё задание
и свой каталог сборки): сборки N и N+1 с признаком дымовой сборки (ключ одного запуска, источник версий на петле; у N+1
лишняя миграция), подпись и проверка N+1 тем же инструментом выпуска, затем установить N, создать сагу с книгой,
обновиться до N+1 — NSIS на Windows, AppImage и `.deb` (с `pkexec` раннера) на Ubuntu, `.rpm` в контейнере Fedora — и
прочитать сагу на N+1. Установщики и журналы — артефакты запуска. Секрет у сценария один — ключ подписи в окружении
`release`, только в шаге подписи; сторонние действия закреплены по коммиту.

Пока у версии Codex из `backend/go.mod` нет пакета Windows, задание Windows останавливается на наборе с этой причиной.

На Windows до сборки установщика задание гоняет тесты копии домов Codex на настоящей Windows:
`go test ./internal/adapters/codex -run 'Copy|Hold' -count=1` в `backend` — тест файла дома, который держит сканер,
идёт только там.

## Как идёт выгрузка в публичный репозиторий

Публичный репозиторий `canonkeeper/desktop-app` — выгрузка открытого дерева монорепозитория по
`open-source/manifest.json`. Своих файлов у него три: `spike/`, `LICENSE`, `README.md`; всё остальное, вместе с
проверкой `scripts/check-forbidden.py`, хуком `scripts/hooks/pre-push` и обоими workflow, приходит выгрузкой.

1. Сверка дерева в монорепозитории: `npm run open-source:check`. Шаг `forbidden` — закрытый список и ключи, шаг
   `generic_rules` — те же общие правила, что у CI публичного репозитория (`scripts/check-forbidden.py --tree` по
   дереву выгрузки: ключи, домашние каталоги настоящих пользователей, адреса почты, публичные IPv4); в выводе — файл и
   вид находки, значение ключа не печатается.
2. Выгрузка — одна команда из чистого монорепозитория в чистый клон:
   `node scripts/open-source/export.mjs --to <клон> --branch export/<дата>` (основа — `main` клона, `--base` меняет
   её). На новой ветке клона она убирает его прежние файлы, кроме своих, кладёт дерево, сценарии `desktop/ci/*.yml` —
   ещё и в `.github/workflows/`, сводит `.gitignore` и добавляет всё в индекс. Ничего не коммитит и не отправляет;
   находка закрытого списка, общих правил или ключа отменяет выгрузку.
3. Сверка в клоне: `git diff --cached --stat` и сами изменения; коммит — от `CanonKeeper <support@canonkeeper.ru>`:
   в истории публичного репозитория нет личных имён и адресов.
4. Отправка ветки: `git push origin export/<дата>`. Хук перед отправкой (`git config core.hooksPath scripts/hooks`)
   гоняет строгий режим с закрытым списком (`CANONKEEPER_FORBIDDEN_LIST`) и закрытым репозиторием
   (`CANONKEEPER_MONOREPO`); без них отправка отказывает.
5. Отправка ветки `export/**` сама запускает оба workflow — «Forbidden content» и «Desktop installers»; вручную —
   `workflow_dispatch` на той же ветке. Ждём, пока оба пройдут.
6. `main` двигается только вперёд, на вершину проверенной ветки: `git push origin export/<дата>:main` — без
   `--force`, отправку не вперёд git отклоняет.

Запросов на слияние в публичном репозитории не открывают: для запроса GitHub делает коммит слияния с именем и адресом
аккаунта, который его открыл, и личность сопровождающего попала бы в историю публичного репозитория. Поэтому workflow не
слушают событие `pull_request`, а сборка ветки идёт по её отправке или вручную.
